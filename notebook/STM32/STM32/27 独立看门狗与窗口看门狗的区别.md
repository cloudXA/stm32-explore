# 独立看门狗与窗口看门狗的区别

## 1. 为什么需要看门狗

嵌入式设备经常需要长时间无人值守运行，程序可能因为以下原因失去正常控制：

- 代码进入死循环；
- 等待某个标志时没有设置超时；
- 通信或外设异常导致程序长期阻塞；
- 指针、栈或内存被破坏；
- 电磁干扰导致程序跑飞；
- RTOS任务死锁或关键任务停止运行。

看门狗的作用可以概括为：

> 程序必须定期证明自己仍然正常；如果在规定时间内没有证明，看门狗就复位STM32，让系统重新启动并尝试恢复。

这个“证明系统正常”的动作通常称为喂狗：

```c
HAL_IWDG_Refresh(&hiwdg);  /* 独立看门狗喂狗 */
HAL_WWDG_Refresh(&hwwdg);  /* 窗口看门狗喂狗 */
```

## 2. 独立看门狗IWDG

IWDG是`Independent Watchdog`的缩写。

### 2.1 为什么叫“独立”

IWDG使用独立的低速内部时钟LSI，不依赖CPU使用的系统主时钟：

```text
CPU和大多数外设：HSE/HSI → PLL → 系统时钟
独立看门狗：      LSI → IWDG
```

即使主时钟异常或CPU程序卡死，LSI仍可让IWDG继续倒计时并最终复位系统。

### 2.2 工作过程

```text
重装载值RLR
    ↓
计数器不断递减
    ↓
在到0之前喂狗 → 重新装载RLR，继续运行
    ↓
没有及时喂狗 → 计数到0，STM32复位
```

IWDG只限制最晚喂狗时间：

```text
早一点喂：允许
正常时间喂：允许
超过期限：复位
```

### 2.3 超时时间

近似计算公式：

```text
IWDG超时时间 ≈ 预分频系数 × (RLR + 1) ÷ LSI频率
```

例如：

```text
LSI约为40kHz
预分频系数为64
RLR取624时，按 `(RLR + 1)` 和40kHz标称值计算为1秒；RLR取625则约1.0016秒
```

则超时时间大约为1秒。

LSI是内部RC振荡器，频率存在误差，因此IWDG超时时间通常不能当作高精度定时器使用。设计时需要保留余量。

### 2.4 主要用途

- 检测程序长时间没有运行到喂狗位置；
- 系统时钟异常时仍能提供复位保护；
- 无人值守设备的故障自动恢复；
- 对喂狗时间精度要求不高的通用可靠性保护。

## 3. 窗口看门狗WWDG

WWDG是`Window Watchdog`的缩写。

### 3.1 什么是“窗口”

WWDG不仅限制最晚喂狗时间，也限制最早喂狗时间：

```text
喂得太早 → 复位
在合法窗口内喂 → 正常
喂得太晚 → 复位
```

因此它可以同时检测：

- 程序运行太慢或卡死，没有及时喂狗；
- 程序跑飞或执行节奏异常，过早运行到喂狗位置。

### 3.2 典型计数过程

假设配置：

```text
初始计数值T = 0x7F
窗口值W     = 0x5F
EWI位置      = 0x40
复位位置     = 0x3F
```

计数器不断递减：

```text
0x7F → 0x7E → …… → 0x60 → 0x5F → …… → 0x41 → 0x40 → 0x3F
```

各区域的含义：

```text
0x7F～0x60：太早，不能喂狗
0x5F～0x40：计数器不大于W且T6仍为1，属于可刷新范围
0x40：      同时可产生提前唤醒中断EWI
0x3F：      系统复位
```

### 3.3 时钟来源

WWDG使用PCLK1经过固定分频和预分频后的时钟：

```text
WWDG计数频率 = PCLK1 ÷ 4096 ÷ 预分频系数
```

例如：

```text
PCLK1 = 36MHz
预分频系数 = 8
```

每次计数所需时间约为：

```text
4096 × 8 ÷ 36MHz ≈ 0.9102ms
```

从`0x7F`减到窗口值`0x5F`大约需要：

```text
(127 - 95) × 0.9102ms ≈ 29.13ms
```

因此开始后的约29.13ms内不能喂狗。

从`0x7F`运行到EWI位置 `0x40` 需要63个计数，约57.34ms；若不刷新，再走一步到 `0x3F` 触发复位，总计约58.25ms。两者不能混成同一个周期。

### 3.4 提前唤醒中断EWI

EWI是`Early Wakeup Interrupt`，表示复位前的最后警告：

```text
计数到0x40
→ 触发WWDG中断
→ 进入HAL_WWDG_EarlyWakeupCallback()
→ 如果不处理，下一步到0x3F就会复位
```

教学实验可以在回调中喂狗：

```c
void HAL_WWDG_EarlyWakeupCallback(WWDG_HandleTypeDef *hwwdg)
{
    HAL_WWDG_Refresh(hwwdg);
    HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_9);
}
```

这样可以观察中断，并阻止系统复位。

但正式产品不宜始终依靠EWI中断无条件喂狗。否则即使主程序卡死，只要中断仍能执行，它就会继续喂狗，使看门狗失去作用。

正式项目中，EWI更适合：

- 记录故障码；
- 保存少量关键状态；
- 关闭电机、继电器等危险输出；
- 不再喂狗，等待硬件复位。

## 4. IWDG与WWDG核心对比

| 对比项 | 独立看门狗IWDG | 窗口看门狗WWDG |
| --- | --- | --- |
| 时钟来源 | 独立LSI低速内部时钟 | PCLK1分频后的时钟 |
| 与系统主时钟的关系 | 相对独立 | 依赖APB1时钟 |
| 计数方式 | 向下递减至0后复位 | 7位计数器向下递减至复位边界 |
| 喂狗过早 | 允许 | 可能立即复位 |
| 喂狗过晚 | 复位 | 复位 |
| 合法喂狗时间 | 超时前均可 | 必须位于指定窗口内 |
| 提前唤醒中断 | 通常没有WWDG这种EWI机制 | 可在0x40产生EWI |
| 时间精度 | LSI误差较大 | 由PCLK1决定，相对更可控 |
| 检测重点 | 程序是否长时间没有正常运行 | 程序是否过早或过晚运行到喂狗位置 |
| 使用难度 | 较简单 | 配置和喂狗时机更严格 |
| 常见用途 | 通用故障恢复、无人值守设备 | 对程序执行周期有严格要求的场景 |

## 5. 应该选择哪一种

### 优先选择IWDG的情况

- 初学看门狗；
- 只需要检测程序卡死或长时间阻塞；
- 系统可能出现主时钟故障；
- 设备长期无人值守；
- 业务执行时间有一定波动；
- 希望配置和维护更简单。

对于普通STM32、ESP8266、传感器和物联网项目，通常先使用IWDG。

### 考虑选择WWDG的情况

- 关键业务必须按照比较固定的周期执行；
- 不仅要检测任务不执行，还要检测任务异常地过早执行；
- 需要复位前提前中断；
- 能够准确分析任务最短和最长执行时间；
- 系统对时间窗口有明确要求。

## 6. 正确的喂狗设计

### 不推荐：无条件喂狗

```c
while (1)
{
    HAL_IWDG_Refresh(&hiwdg);
}
```

这只能证明喂狗语句仍在运行，不能证明传感器、通信和其他关键业务正常。

### 推荐：健康检查通过后喂狗

```c
while (1)
{
    Sensor_Process();
    Network_Process();
    UART_Process();

    if (sensor_ok && network_task_ok && uart_task_ok)
    {
        HAL_IWDG_Refresh(&hiwdg);
    }
}
```

其含义是：

```text
关键模块全部正常
→ 才允许喂狗

某个关键模块长期异常
→ 停止喂狗
→ 看门狗超时
→ STM32复位并尝试恢复
```

对于WWDG，还必须保证健康检查完成的时刻位于合法窗口内。

## 7. 看门狗不能代替错误处理

看门狗是系统最后一道恢复手段，不应该把所有异常都交给复位处理。

例如网络断开时，应优先：

```text
检测TCP断开
→ 尝试重连TCP
→ 必要时重新连接Wi-Fi
→ 必要时复位通信模块
→ 软件彻底失去控制时才由看门狗复位STM32
```

合理的故障恢复层次是：

```text
业务重试
→ 外设重新初始化
→ 通信模块复位
→ MCU看门狗复位
```

## 8. 调试注意事项

- 启动看门狗后，程序停在断点时看门狗可能仍继续计数并造成复位。
- 调试阶段可以配置DBGMCU在CPU暂停时冻结看门狗。
- 需要检查RCC复位标志，判断本次启动是否由IWDG或WWDG导致。
- 看门狗一旦启动，很多STM32型号只能通过系统复位停止。
- 初始化和Flash擦写等耗时操作必须计入超时时间设计。
- IWDG使用的LSI存在误差，超时时间必须保留安全余量。
- WWDG不能在窗口开启前提前刷新，否则会直接造成复位。

复位原因可通过RCC标志判断：

```c
if (__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST) != RESET)
{
    /* 上一次由独立看门狗复位 */
}

if (__HAL_RCC_GET_FLAG(RCC_FLAG_WWDGRST) != RESET)
{
    /* 上一次由窗口看门狗复位 */
}

__HAL_RCC_CLEAR_RESET_FLAGS();
```

## 9. 最简单的记忆方法

```text
IWDG：
有最晚期限，没有最早限制；
使用独立LSI时钟；
重点防止程序长时间不工作。

WWDG：
既有最早时间，也有最晚时间；
必须在合法窗口内喂狗；
可以检测程序运行得过早或过晚。
```

一句话总结：

> IWDG像“下班前交作业即可”；WWDG像“必须在规定时间段内交作业，太早和太晚都不合格”。普通项目优先使用IWDG，对执行周期有严格要求时再考虑WWDG。

## 10. 教程对比表补充

教程还从计数器位数、复位条件和应用场景进行了归纳：

| 对比点 | 独立看门狗IWDG | 窗口看门狗WWDG |
| --- | --- | --- |
| 时钟源 | 独立LSI，STM32F103典型值约40kHz，精度较低 | 外设总线时钟分频，STM32F103使用PCLK1，精度相对更高 |
| 复位条件 | 递减计数器减到0 | 在窗口外过早喂狗，或者计数器继续减到0x3F |
| 提前中断 | 没有WWDG这种EWI提前唤醒中断 | 计数到0x40时可产生EWI中断 |
| 递减计数器 | 12位，重装载值范围0～4095 | 7位，但正常工作有效范围为0x7F～0x40 |
| 主要用途 | 防止程序跑飞、死循环、死机 | 监控程序执行节奏，检测执行过早或过晚 |

### 10.1 为什么IWDG说是12位

IWDG重装载寄存器`RLR`的有效计数部分是12位，因此可配置：

```text
0～4095
```

计数值越大、预分频越大，允许不喂狗的最长时间就越长。

### 10.2 为什么WWDG说是7位，却只看到127～63

WWDG计数器使用低7位：

```text
最大值：0x7F = 127
```

但是最高有效位`T6`必须保持为1，WWDG才能处于正常计数区域。因此实际关注的范围是：

```text
0x7F～0x40：T6仍为1的正常递减区域
0x40：可产生EWI提前唤醒中断，也仍可刷新
0x3F：进入复位条件
```

所以教程写“最大计数范围127～63”，是在强调窗口看门狗真正参与工作的有效区间，不是普通的0～127完整计数用途。

### 10.3 PCLK1和PCLK3为什么会有两种说法

WWDG挂在哪条外设总线上取决于具体STM32系列：

```text
本实验STM32F103：WWDG时钟来自PCLK1
部分其他STM32系列：可能来自PCLK3或其他外设总线
```

因此不能脱离芯片型号记忆。应查看当前芯片的参考手册或CubeMX时钟树。

对本实验的STM32F103，应使用：

```text
WWDG计数频率 = PCLK1 ÷ 4096 ÷ 预分频系数
```

### 10.4 “IWDG没有中断”应该怎样理解

这里是说STM32F103的IWDG没有像WWDG那样的EWI提前唤醒中断：

```text
IWDG超时 → 直接产生系统复位
WWDG到0x40 → 可先产生EWI；继续到0x3F → 系统复位
```

## 11. 选择和验证步骤

### 选择IWDG

当目标是“程序无论因主循环、任务或主时钟异常而失去响应，都应在最长时间后复位”时，优先考虑IWDG。先列出所有正常情况下最长阻塞时间，再设置带余量的超时；不要为了让程序不复位而在每个循环无条件刷新。

### 选择WWDG

当系统存在明确执行周期，既要检测太晚也要检测异常过早的刷新路径时才考虑WWDG。应计算最早合法时间和EWI/复位时间，把刷新点放在窗口中部，而不是贴着 `W` 或 `0x40` 边界。

### 必做验证

1. 正常健康状态下持续运行，不发生误复位。
2. 故意停止刷新，确认超时后复位。
3. WWDG故意过早刷新，确认能检测节奏异常。
4. 上电读取 `RCC_FLAG_IWDGRST` / `RCC_FLAG_WWDGRST` 并记录复位原因。
5. 在调试器断点、Flash擦写、网络超时和最低/最高温度时验证时间余量。

## 12. 最重要的工程结论

看门狗不是“定时执行某个业务”的普通定时器，而是故障恢复机制。刷新动作必须代表系统真的健康；EWI中永远刷新会掩盖主程序卡死，IWDG在主循环顶部无条件刷新也可能掩盖后续任务失效。

因此需要在IWDG超时前由正常程序完成喂狗，不能等待一个“即将复位中断”再补救。
