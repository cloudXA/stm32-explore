严格来说，这不是 UTF-8 编码不支持换行，而是该 App 不会把输入框里的 \n 转换成换行字节。以后遇到串口命令没反应，可以先查看实际发送的十六进制字节，这是很实用的排查方法。
![4cb50df59dff6245b6fde5498fd01a3a.png](../_resources/4cb50df59dff6245b6fde5498fd01a3a.png)

open: 6F 70 65 6E 0A(hex)
close: 63 6C 6F 73 65 0D 0A (hex)

原因已经很明确：写入 UUID 选错了。

截图中：

```text
读取 UUID：FFE1  ← 正确
写入 UUID：2A02  ← 错误
```

HC-08 默认使用：

```text
服务 UUID：FFE0
读/写/通知特征 UUID：FFE1
```

而 `2A02` 是蓝牙标准里的“Peripheral Privacy Flag”，不是串口透传通道，所以模块拒绝写入，应用直接显示“发送失败”。[HC-08 官方手册](https://www.hc01.com/downloads/HC-08A%20version%20english%20datasheet.pdf)也说明 `FFE1` 支持 `read / notify / write_without_response`；`2A02` 的定义可见[蓝牙 SIG 官方编号表](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Assigned_Numbers/out/en/index-en.html)。

修正步骤：

1. 点击“写入 UUID”这一栏。
2. 选择：

```text
0000ffe1-0000-1000-8000-00805f9b34fb
```

3. 如果能选择写入方式，选择：

```text
Write Without Response
写入无响应
```

4. “读取 UUID”继续保持 `FFE1`。
5. 再发送 `open`。

另外，你的 STM32 程序需要收到换行才处理命令。UUID修正后，如果显示“发送成功”但 GPIO 没动作，点击发送框旁边的设置按钮，开启：

```text
结尾添加 LF
```

或：

```text
结尾添加 CRLF
```

最终应该发送的实际数据是：

```text
open\n
close\n
```

但要在应用设置中添加真实换行，不能在输入框直接输入普通字符 `/n`。

## BLE与UART分别处在哪一段

HC-08一侧通过BLE GATT特征与手机通信，另一侧通过TTL UART与STM32通信：

```text
手机App写入FFE1特征
→ HC-08收到BLE数据
→ HC-08从TX脚输出UART字节
→ STM32 USART接收
→ 解析open/close
→ 控制PB8及外部模块
```

FFE0/FFE1是该模块固件约定的服务/特征，不是所有BLE串口模块都通用。换模块时必须重新查看它广播的服务和特征属性。

## 接线与测试步骤

1. 先确认HC-08供电、电平、TX/RX交叉和共地。
2. 用PC串口先验证STM32能识别 `open\n`、`close\n`。
3. 单独验证手机能连接HC-08，并选择FFE1特征写入。
4. 使用十六进制显示确认实际发送的是 `6F 70 65 6E 0A` 或带CRLF的对应字节。
5. 把BLE与STM32合起来，先让STM32回显收到的原始字节，再启用GPIO业务。
6. 对命令设置最大长度和超时，收到未知命令时返回错误信息。

## 应用协议建议

`open` / `close` 是自己定义的应用层协议，不属于蓝牙或UART。建议统一使用一行一条命令：

```text
open\r\n
close\r\n
status?\r\n
```

解析时忽略结尾的CR/LF，但不能依赖“手机一次写入就一定对应STM32一次完整接收”。仍应按字节累计，遇到行结束符后再处理。

如果PB8最终控制继电器和市电负载，先用LED完成全部软件验证；市电部分必须采用合格隔离、外壳、端子和保护，不在面包板上直接实验。
