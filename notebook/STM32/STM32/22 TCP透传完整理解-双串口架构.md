# 22 TCP透传完整理解 -- 双串口架构

## 先看总图

```mermaid
flowchart LR
  A["电脑串口助手"] <-->|USB| B["CH340 USB转串口"]
  B <-->|USART2 115200| C["STM32"]

  C <-->|USART1 9600<br/>AT指令 + TCP透传数据| D["ESP8266"]
  D <-->|Wi-Fi| E["路由器 mi"]
  E <-->|局域网 TCP| F["电脑网络助手<br/>TCP Server 10.154.61.205:8880"]
```

你这次其实不是"一个串口变复杂了"，而是系统分成了两条路：

`USART2 + CH340` 是给人看的调试通道。  
STM32 把日志、心跳、ESP8266 返回内容打印到这里，所以你能在串口助手里看到：

```text
=== STM32 UART2 Ready ===
Joining WiFi...
[ESP8266]: OK
[UART2] heartbeat
```

`USART1 + ESP8266` 是给网络用的通信通道。  
STM32 通过 USART1 对 ESP8266 说："连 WiFi、连 TCP 服务器、进入透传模式"。ESP8266 负责真正的 WiFi 和 TCP 网络通信。

## AT 指令是什么

ESP8266 可以理解成一个带 WiFi 功能的小模块。STM32 自己不会直接连 WiFi，所以它要通过串口发命令控制 ESP8266。

这些命令就是 AT 指令，例如：

```c
AT+CWJAP="mi","12345678"
```

意思是：让 ESP8266 连接名叫 `mi` 的 WiFi，密码是 `12345678`。

```c
AT+CIPSTART="TCP","10.154.61.205",8880
```

意思是：让 ESP8266 去连接电脑上的 TCP 服务器，IP 是 `10.154.61.205`，端口是 `8880`。

所以 AT 指令属于"控制命令"。它不是你最终想传的业务数据，而是 STM32 用来指挥 ESP8266 干活的语言。

## TCP 又是什么

TCP 是电脑网络助手和 ESP8266 之间建立的一条"可靠字节通道"。

当连接成功后，关系变成这样：

```text
电脑网络助手  <--TCP连接-->  ESP8266  <--串口USART1-->  STM32
```

你在网络助手发 `led1`，实际路线是：

```text
网络助手发送 led1
        ↓ TCP
ESP8266 收到 led1
        ↓ USART1 串口吐给 STM32
STM32 收到 l e d 1
        ↓ 判断命令
PB8 输出低电平，LED 点亮
```

你在 STM32 里回传 `LED ON\r\n`，路线反过来：

```text
STM32 通过 USART1 发 LED ON
        ↓
ESP8266 通过 TCP 发给电脑网络助手
        ↓
网络助手显示 LED ON
```

## 透传模式怎么理解

普通模式下，STM32 发给 ESP8266 的内容会被 ESP8266 当成 AT 指令解析。

透传模式打开后：

```text
AT+CIPMODE=1
AT+CIPSEND
```

ESP8266 进入一种"搬运工模式"。之后 STM32 从串口发什么普通数据，ESP8266 就通过 TCP 发出去；电脑网络发来的数据，ESP8266 也原样从串口吐给 STM32。

所以透传模式下，ESP8266 像一根"无线串口延长线"。

## 这次代码的组织逻辑

你的 [main.c](D:/STM32/uart2_test/Core/Src/main.c) 可以按这个顺序理解：

1. 初始化硬件  
   配置系统时钟、GPIO、USART1、USART2。

2. 打开 USART2 调试窗口  
   STM32 先通过 CH340 打印启动信息，证明程序活着、USART2 正常。

3. 打开 USART1 接收中断  
   ESP8266 发回来的每个字节，STM32 都能收到。

4. 发送 AT 指令连接 WiFi  
   STM32 发 `AT+CWJAP`，等待 ESP8266 返回 `WIFI CONNECTED`、`WIFI GOT IP`、`OK`。

5. 查询 ESP8266 IP  
   用 `AT+CIFSR` 看 ESP8266 自己拿到的局域网 IP，方便确认它和电脑是不是在同一网段。

6. 连接电脑 TCP Server  
   发 `AT+CIPSTART="TCP","10.154.61.205",8880`。这一步成功，网络助手里才会出现连接。

7. 成功后进入透传模式  
   发 `AT+CIPMODE=1` 和 `AT+CIPSEND`。成功后网络数据和串口数据就可以互相转发。

8. 主循环一直干三件事  
   处理网络发来的 `led1` / `led0`；  
   把 ESP8266 收到的数据转发到 USART2，方便你看；  
   如果没连上 TCP，就打印 heartbeat，证明程序没死。

## 为什么用"一个字节一个字节接收"

这是初学者最容易懵的点。

串口不是"你发一整句，我就一次收到一整句"。TCP 也不是"你发 `led1`，STM32 一定一次收到完整 `led1`"。

实际可能是：

```text
第一次收到: l
第二次收到: e
第三次收到: d
第四次收到: 1
```

也可能是：

```text
第一次收到: le
第二次收到: d1
```

所以代码不能天真地只写：

```c
strcmp(buffer, "led1")
```

因为你不一定刚好拿到完整字符串。

我们这次加的是"字节流状态机"：每收到一个字符，就看看它是不是正在组成 `led1` 或 `led0`。只要连续匹配到完整命令，就设置 LED 动作。

## 为什么中断里不直接做很多事

USART 接收中断很像"有人敲门"。中断函数应该快点处理完，不要在里面做很慢的事情，比如长时间打印、复杂判断、大量延时。

所以这次代码思路是：

```text
中断里：
  收一个字节
  简单记录
  设置标志位
  重新开启下一次接收

主循环里：
  真正处理 LED
  打印日志
  回传网络数据
```

这就是嵌入式里很重要的思想：中断轻，主循环重。

## 你这次遇到的问题本质

之前不是波特率不对。因为你已经能在串口助手看到正常英文日志，说明 USART2 和 CH340 的 `115200 8-N-1` 是通的。

真正的问题在电脑网络侧：

| 现象 | 更可能的问题 |
|---|---|
| 串口助手能看到 heartbeat | STM32 程序在跑 |
| ESP8266 能 `WIFI GOT IP` | WiFi 已连接 |
| `AT+CIPSTART` 返回 `ERROR/CLOSED` | TCP 没连上电脑 |
| 禁用 VPN / Norton 后好了 | 电脑防火墙、VPN、路由策略拦截了连接 |
| `Test-NetConnection` 后来变 True | 电脑 8880 端口监听正常了 |

所以你这次调通的核心链路是：

```text
不是修一个串口
而是打通了：
STM32 串口 → ESP8266 AT → WiFi → TCP → Windows 防火墙/网络助手
```

## 初学者怎么理解最稳

你可以按五层来学，不要一口气全塞进脑子里：

1. UART 层  
   STM32 和外设之间就是 TX/RX 两根线，一边发，一边收。

2. 调试层  
   `USART2 + CH340` 是你的"眼睛"，用来看到 STM32 现在在干嘛。

3. 模块控制层  
   `USART1 + AT指令` 是 STM32 在命令 ESP8266。

4. 网络层  
   ESP8266 负责连 WiFi、拿 IP、连电脑 TCP Server。

5. 应用层  
   你自己定义 `led1` 是开灯，`led0` 是关灯。

你现在已经从"串口收发"跨到了"串口控制网络模块，再通过网络控制 GPIO"。这一步很关键，因为它把嵌入式里最常见的几个概念都串起来了：外设通信、中断、状态机、网络连接、应用协议。

## main()、中断、透传三者的分工

### 1. `main()`：网络连接的"流程控制者"

`main()` 按顺序通过 USART1 给 ESP8266 发送 AT 指令：

```text
连接 Wi-Fi
    ↓
查询 ESP8266 的 IP
    ↓
连接电脑的 TCP Server
    ↓
开启透明传输
    ↓
进入正常收发阶段
```

与此同时，通过 USART2 把每一步的状态打印到 CH340 串口助手：

```c
UART2_DebugPrint("Joining WiFi...\r\n");
UART2_DebugPrint("Connecting TCP server...\r\n");
```

所以不是 UART2 帮助建立 TCP，而是：

- USART1：真正控制 ESP8266。
- USART2：记录并展示连接过程。
- `main()`：组织整个执行顺序。

### 2. 中断函数：实时接收 ESP8266 返回的数据

STM32 每次从 USART1 接收一个字节，接收完成后进入：

```c
HAL_UART_RxCpltCallback()
```

在连接阶段，ESP8266 会返回：

```text
WIFI CONNECTED
WIFI GOT IP
OK
ERROR
>
```

中断函数把这些字节拼成一行，再识别关键内容。例如：

```c
if (strstr((char *)UART_RX_BUF, "WIFI GOT IP") != NULL)
{
    WIFI_GOT_IP_Flag = 1;
}
```

`main()` 正在等待这个标志：

```c
while (!WIFI_GOT_IP_Flag && 未超时)
{
}
```

因此两者实际上是在配合：

```text
main() 发 AT 指令并等待
          ↓
ESP8266 返回结果
          ↓
USART1 接收中断识别结果并设置标志
          ↓
main() 发现标志改变，继续执行下一步
```

### 3. TCP连接后：中断开始处理网络业务数据

收到 `>` 后，程序认为已经进入透明传输：

```c
ESP_TRANSPARENT_MODE_Flag = 1;
```

从这时开始，USART1 收到的内容不再主要是 AT 回复，而是电脑通过 TCP 发来的业务数据：

```text
电脑 Python/网络助手
       ↓ TCP
ESP8266
       ↓ USART1
STM32 接收中断
```

中断函数会对每个字节做两件事：

```c
LED_ParseByte(UART_RX_BUF[0]);
```

识别 `led1` 或 `led0`。

同时：

```c
UART2_FORWARD_BUF[...] = UART_RX_BUF[0];
```

把数据暂存起来，之后由主循环通过 USART2 转发给串口助手查看。

最终可以这样概括：

> `main()` 通过 USART1 控制 ESP8266 完成 Wi-Fi 和 TCP 连接，通过 USART2记录运行状态；USART1 接收中断实时处理 ESP8266 的 AT 回复，进入透传后再处理电脑发来的 TCP 业务数据。

还有一点很重要：中断函数不直接做太多耗时工作。它识别到 `led1` 后只设置：

```c
LED_COMMAND_PENDING = 1;
```

真正的 GPIO 点灯由主循环完成：

```c
LED_ProcessPending();
```

这就是常见的嵌入式设计：

```text
中断：快速收数据、记状态
主循环：执行具体业务
```

### 这次至少要弄懂什么

目前不必马上研究 USART 寄存器，但下面这条链必须能够讲清楚：

```text
ESP8266 发出一个字节
        ↓
USART1 硬件收到这个字节
        ↓
触发串口接收中断
        ↓
HAL_UART_RxCpltCallback() 被调用
        ↓
程序读取 UART_RX_BUF[0]
        ↓
解析字节、写入环形缓冲区
        ↓
重新调用 HAL_UART_Receive_IT()
        ↓
等待下一个字节
```

尤其要理解下面四点。

#### 1. 为什么每次只接收一个字节

代码启动接收：

```c
HAL_UART_Receive_IT(&huart1, &UART_RX_BUF[0], 1);
```

最后的 `1` 表示本次只接收一个字节。

例如网络助手发送：

```text
led1
```

STM32 可能经历四次中断：

```text
第1次：l
第2次：e
第3次：d
第4次：1
```

中断不会天然知道这四个字节属于同一条命令，所以代码需要状态机记录"目前匹配到了哪里"。

#### 2. 中断接收需要反复启动

一次：

```c
HAL_UART_Receive_IT(..., 1);
```

只预约一次接收。

收到一个字节并进入回调后，这次任务就完成了。因此回调末尾必须再次执行：

```c
HAL_UART_Receive_IT(&huart1, &UART_RX_BUF[0], 1);
```

这相当于告诉硬件：

> 上一个字节处理完了，请继续通知我下一个字节。

如果忘记重新调用，程序通常只能收到第一个字节。

#### 3. TCP 不提供"消息边界"

电脑发送一次 `led1`，不代表 STM32 一定一次收到完整的 `led1`。

可能是：

```text
"led1"
```

也可能分成：

```text
"le" + "d1"
```

甚至：

```text
"l" + "e" + "d" + "1"
```

多条命令也可能合并：

```text
"led1led0"
```

TCP只承诺：

- 字节不会无故乱序。
- 丢失的数据会尽量重传。
- 它不承诺你发送一次，对方就接收一次。

所以当前代码按字节解析是合理的：

```text
状态0：等待 l
状态1：等待 e
状态2：等待 d
状态3：等待 1 或 0
```

#### 4. 为什么中断里不直接处理所有业务

中断的原则是：

> 越短越好，收下数据，记录事件，然后尽快退出。

如果在中断里进行长时间打印、延时或复杂业务，可能导致后面的字节来不及处理。

因此当前代码分成：

```text
接收中断：
    收字节
    解析命令
    设置 LED_COMMAND_PENDING

主循环：
    读取 LED_COMMAND_PENDING
    操作 GPIO
    打印结果
    回传 TCP 数据
```

这和前端有一点相似：

```text
串口中断        ≈ 事件监听器
pending 标志    ≈ 待处理状态
main 主循环     ≈ event loop
LED_Process...  ≈ 业务处理函数
```

这个类比并不完全等价，但很适合建立第一层认识。

### 哪些细节现在可以暂缓

目前可以先不深究：

- USART 的 SR、DR、CR1 寄存器每一位。
- NVIC 的全部优先级细节。
- HAL 内部状态机的完整源码。
- TCP 拥塞控制算法。
- TCP 重传、滑动窗口的数学细节。
- ESP8266 固件内部如何实现 TCP/IP 协议栈。

这些以后遇到性能、丢包、并发或实时性问题时再深入，学习效果会更好。

## 建议采用"三层学习法"

### 第一层：会使用

先保证你能完成：

- 串口发送和接收。
- ESP8266 连接 Wi-Fi。
- 建立 TCP。
- 电脑控制 LED。
- STM32 向电脑返回状态。

你现在已经基本完成这一层。

### 第二层：会解释和修改

接下来重点练习：

- 把 `led1` 改成其他命令。
- 增加 `status?`。
- 处理一条命令被拆成多个字节的情况。
- 处理多条命令连续到达。
- 缓冲区满了怎么办。
- TCP 断开后如何重新连接。

这是你现在最应该进入的阶段。

### 第三层：深入底层

当你能修改业务后，再学习：

- UART 中断标志和寄存器。
- DMA + 空闲中断接收。
- 环形缓冲区的并发安全。
- 中断优先级。
- TCP连接状态和断线重连。
- FreeRTOS 任务与消息队列。

这样学习，底层知识会有实际问题作为支撑，不会变成纯背诵。

4. 暂时注释掉回调中的下一次接收：

```c

```

观察为什么只能收到一个字节，然后立即恢复。

5. 增加一个新命令：

```text
status?
```

让 STM32 返回当前 LED 状态。

如果你能亲手完成这五个实验，你对字节流的理解会比单纯阅读 HAL 源码扎实得多。

所以我的建议是：

> 不需要停下整个项目钻到底，但也不要完全跳过。花一两个学习单元把"单字节中断、重新启动接收、状态机、主循环处理"亲手验证，然后继续做项目；等遇到性能问题，再升级到 DMA、空闲中断和更正式的协议解析。

## 一句话总结

CH340 是给人看的串口，ESP8266 是给网络用的串口；AT 指令负责配置连接，TCP 透传负责搬运数据，STM32 主循环负责解释 led1/led0 并控制 GPIO。
